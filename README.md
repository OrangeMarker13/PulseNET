# PulseGrid

PulseGrid is an emergency resource planning app I built using Python and Streamlit. The main idea is to help figure out where ambulances should be placed in a city based on where emergency demand is highest.

The app takes emergency-demand data, geographic information, weather information, and emergency facilities, then uses that information to find locations where ambulances would provide better coverage.

PulseGrid also includes a quantum optimization experiment using QAOA. The quantum part is kept relatively small so the program stays practical to run. A classical optimization method is also included, so the app still works if the quantum part is unavailable.

This project is meant for research and experimentation. It is not a real emergency dispatch system.

## What PulseGrid Does

PulseGrid goes through several steps when an analysis is run:

1. You choose a city.
2. You choose the analysis settings.
3. You choose how many ambulances to place.
4. You either upload EMS data or use simulated demo data.
5. The app gets geographic and weather information.
6. The EMS records are turned into demand zones.
7. The app estimates predicted demand for each zone.
8. Emergency facilities are found using OpenStreetMap.
9. A classical optimization method chooses facility locations.
10. A smaller quantum optimization problem is created and sent to QAOA when Qiskit is available.
11. Route estimates are used to evaluate the selected locations.
12. The app compares the optimized deployment with a baseline.
13. The results are shown using metrics, tables, and an interactive map.

## Project Files

PulseGrid is intentionally kept to nine main files.

```text
PulseGrid/
│
├── app.py
├── config.py
├── demand.py
├── optimization.py
├── quantum_engine.py
├── services.py
├── map.py
├── requirements.txt
└── README.md
```

I kept the project small because having many files that do the same thing makes the project harder to understand and maintain.

### app.py

This is the main file for the application.

It controls the Streamlit interface and connects the other parts of PulseGrid together.

It handles things such as:

* The main page
* The visual design
* City selection
* Analysis settings
* Ambulance count
* Date and time settings
* EMS CSV uploads
* Demo demand
* Running the analysis
* Showing results
* Streamlit session state
* Caching external data

The main PulseGrid analysis starts when the user clicks the Run PulseGrid Analysis button.

### config.py

This file stores settings used throughout the project.

Examples include:

* Supported cities
* Default ambulance count
* Maximum ambulance count
* Analysis modes
* OpenStreetMap search radius
* Routing timeout

I put these settings in one place so they do not have to be repeated throughout the code.

### demand.py

This file handles emergency-demand data.

It works with either uploaded EMS records or simulated demo records.

The EMS data needs information for:

```text
timestamp
latitude
longitude
```

The program also accepts common alternatives such as:

```text
datetime
date_time
call_time
lat
lon
lng
```

The file checks the data, removes invalid records, converts timestamps, and gets information such as:

* Hour
* Day of the week
* Month

It also creates the geographic demand zones used by the rest of the application.

### Demo Data

PulseGrid includes a demo-data option so the app works even when someone does not have a real EMS dataset.

The demo data is generated by the program around several geographic locations.

The demo data is simulated.

It does not represent real emergency calls and should never be presented as real emergency data.

### Demand Zones

PulseGrid divides the area around the selected city into a grid.

The EMS records are placed into the appropriate grid cells.

Each zone gets information such as:

* Latitude
* Longitude
* Historical demand
* Predicted demand
* Priority

The zones with more demand receive higher priority.

The program keeps historical demand and predicted demand separate so it is clear which values came from the original data and which values were calculated by the program.

### optimization.py

This file handles the classical optimization part of PulseGrid.

It first calculates geographic distances using the Haversine formula.

It then creates a distance matrix between demand zones and candidate facilities.

The optimizer uses predicted demand as a weight. This means a location close to a high-demand zone has more importance than a location close to a low-demand zone.

The greedy optimizer then chooses facilities one at a time.

The goal is to place the requested number of ambulances in locations that provide good overall coverage.

This part of the program mainly uses geographic distance because calculating driving routes for every possible facility and demand-zone combination would require many route requests.

### Route Evaluation

After the deployment is selected, PulseGrid uses route estimates to get a more realistic idea of how long it might take to travel between a selected facility and a demand zone.

This creates an important difference:

```text
Optimization
    ↓
Geographic distance

Final evaluation
    ↓
Estimated driving route
```

The geographic distance is used to make the optimization manageable.

The route estimate is used when evaluating the final result.

The route times are estimates and are not guaranteed emergency response times.

### quantum_engine.py

This file contains the quantum optimization experiment.

The goal is to test whether a quantum optimization approach can help with the facility-selection problem.

The program creates a binary decision for each candidate facility.

For example:

```text
1 = select facility
0 = do not select facility
```

The quantum objective considers:

* How useful a facility is
* How close it is to demand
* How much it overlaps with other facilities
* How many facilities should be selected

The problem is intentionally limited in size.

This is important because increasing the number of qubits makes quantum optimization much harder to run.

PulseGrid uses QAOA when the required Qiskit packages are installed and the quantum backend works.

If Qiskit is unavailable or something goes wrong, the program returns a failure result instead of crashing.

The classical optimizer remains available.

The app should never say that a quantum optimization successfully ran if it did not.

### services.py

This file handles the outside services used by PulseGrid.

It keeps the API code in one place instead of having separate weather, hospital, traffic, road, and location files.

It handles:

* OpenStreetMap Nominatim
* National Weather Service
* OpenStreetMap Overpass
* OSRM

These services provide things such as:

* City coordinates
* Weather
* Fire stations
* Hospitals
* Roads
* Driving-route estimates

The functions in this file use timeouts and check whether the responses contain the information PulseGrid needs.

If an outside service fails, PulseGrid should report the problem and continue using the information it still has.

For example, if the weather service is unavailable, the rest of the analysis should still run when possible.

### map.py

This file handles the interactive map.

The map shows things such as:

* The selected city
* Demand zones
* High-priority areas
* EMS facilities
* Hospitals
* Candidate facilities
* Selected ambulance locations

Different types of locations use different markers so they are easier to tell apart.

Future map features should go into this file instead of putting map code into the optimization or demand modules.

### requirements.txt

This file contains the Python packages needed to run PulseGrid.

Install them with:

```bash
pip install -r requirements.txt
```

### README.md

This file explains the project, how the code is organized, how to run it, and some of the limitations of the current version.

## What the Results Show

The application shows several different results after an analysis finishes.

### Demand

The app shows:

* Total predicted demand
* Number of demand zones
* Historical demand
* Predicted demand
* Zone priority

### Facilities

The app shows:

* Number of EMS facilities
* Number of hospitals
* Candidate locations
* Selected deployment locations
* Classical deployment locations

### Response Time

When route information is available, PulseGrid calculates an estimated average response time for the deployment.

The app also compares this with the baseline deployment.

The percentage improvement is calculated from the difference between the baseline and optimized results.

### Coverage

The program calculates how much predicted demand falls within the configured response-time threshold.

Coverage is shown as a percentage.

## Baseline vs. Optimized Deployment

PulseGrid compares the optimized ambulance placement with a baseline.

The baseline gives the program something to compare against instead of only showing the final optimization result.

The comparison includes estimated response time and demand coverage.

A better result in the application means the estimated deployment performs better according to the assumptions and data used for the analysis.

It does not mean the deployment would always perform better in a real emergency.

## What Happens When Something Fails?

PulseGrid is designed so one failed service does not take down the whole program.

For example:

```text
Weather fails
    ↓
Weather is marked unavailable
    ↓
Other analysis continues
```

Another example:

```text
QAOA fails
    ↓
Quantum result is marked unavailable
    ↓
Classical deployment remains available
```

The same idea applies to other optional external services.

This is important because PulseGrid depends on services outside the program itself.

## Why There Are Two Optimization Methods

I included both a classical and a quantum approach because one of the goals of PulseGrid is to explore how different optimization methods handle the same facility-placement problem.

The classical optimizer provides a dependable method for producing a deployment.

The quantum optimizer provides a smaller research experiment using QAOA.

The quantum method is not included simply to make the project sound more advanced. The point is to create a measurable comparison between two different approaches.

Future versions should compare them using the same datasets and evaluation methods.

## Limitations

PulseGrid is still a prototype, so there are several things it does not model perfectly.

### Traffic

The current route estimates do not fully represent real-time traffic.

### Road Closures

The program does not fully account for temporary road closures or emergency road restrictions.

### Ambulance Availability

The current version does not fully model whether individual ambulances are already responding to another call.

### Hospital Capacity

The current version does not model real-time hospital capacity.

### Dispatch

PulseGrid does not act as a live dispatch system.

It analyzes possible resource placements.

### Demand Prediction

The predicted-demand system is still a prototype.

It needs to be tested against larger and validated historical datasets before drawing strong conclusions from it.

### Geographic Distance

The classical optimization uses geographic distance as part of its cost calculation.

Actual driving time depends on roads, traffic, intersections, closures, and many other factors.

### Quantum Computing

The quantum optimization experiment is limited in size.

Larger quantum problems require more computational resources and are not automatically better.

## Running PulseGrid

First, install Python.

Then create a virtual environment:

```bash
python -m venv .venv
```

On Windows:

```bash
.venv\Scripts\activate
```

On macOS or Linux:

```bash
source .venv/bin/activate
```

Install the dependencies:

```bash
pip install -r requirements.txt
```

Then start the app:

```bash
streamlit run app.py
```

Streamlit should open PulseGrid in your browser.

## EMS CSV Format

A basic EMS CSV should look like:

```csv
timestamp,latitude,longitude
2026-08-01 08:15:00,35.2271,-80.8431
2026-08-01 09:42:00,35.2140,-80.8320
2026-08-01 11:03:00,35.2400,-80.8500
```

The example values above are only examples.

They should not be treated as real emergency records.

The program accepts several common column-name variations, including:

```text
timestamp
datetime
date_time
call_time
latitude
lat
longitude
lon
lng
```

Invalid timestamps and invalid geographic coordinates are removed during data cleaning.

## Important Data Rules

PulseGrid should always keep the difference between real and simulated data clear.

If demo data is being used, the interface should say so.

The program should never make simulated emergency records look like real EMS records.

The same rule applies to predicted demand.

Predicted demand is an output of the model. It is not automatically a real-world measurement.

## Development Rules

When changing PulseGrid, the first step should be checking the existing nine files.

Before creating a new file, check whether the feature already belongs in one of the existing modules.

Some important rules are:

* Do not create duplicate API clients.
* Do not create another optimization module.
* Do not create another weather module.
* Do not create another hospital module.
* Do not create another road or traffic module.
* Keep simulated data clearly labeled.
* Keep historical and predicted demand separate.
* Do not claim QAOA ran when it did not.
* Do not let an optional service failure crash the entire app.
* Keep the classical optimizer available.
* Keep UI controls connected to the actual analysis.
* Avoid unnecessary new dependencies.
* Preserve working functionality when changing the interface.
